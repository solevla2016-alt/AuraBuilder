# Logic Graph: логика страницы (ТЗ п.6.4, п.4.2)

Бизнес-логика строится визуально: событие проходит через условия к
действиям. Экспортируется в чистый JavaScript без зависимости от
редактора — сайт с логикой должен работать годами без платформы.

## Устройство

| Что | Где |
|---|---|
| Типы нод | `apps/logic/nodes.py` |
| Разбор и проверка графа | `apps/logic/graph.py` |
| Компиляция в JavaScript | `apps/logic/compiler.py` |
| API редактора | `apps/logic/views.py` |

Граф хранится в версии документа проекта под ключом `logic`: логика
описывает поведение той же страницы, и версионировать её отдельно
значило бы забыть, какая логика соответствовала какой странице.

```json
{
  "nodes": [
    {"id": "n1", "type": "trigger.click", "props": {"blockId": "b1"}},
    {"id": "n2", "type": "condition.property",
     "props": {"source": "data.cart.count", "operator": "gt", "value": "0"}},
    {"id": "n3", "type": "action.message", "props": {"text": "Спасибо!"}}
  ],
  "edges": [
    {"source": "n1", "target": "n2", "branch": ""},
    {"source": "n2", "target": "n3", "branch": "yes"}
  ]
}
```

## Роли нод

Роль важнее конкретного типа, и проверяется компилятором:

* **Активатор** (Triggers) — вход графа. Входящая связь запрещена:
  он начинает цепочку сам.
* **Условие** — ровно две ветки, «да» и «нет». Связь без пометки
  ветки — ошибка.
* **Действие** — конец цепочки. Исходящая связь запрещена.

Собственная терминология ТЗ: Triggers — «Активаторы», Webhooks —
«Сигнальные мосты», Collections — «Узлы данных».

## Типы нод

**Активаторы:** «При клике», «При загрузке страницы», «Сигнальный мост».
**Условия:** «Если условие» (сравнение `eq`, `neq`, `gt`, `gte`, `lt`,
`lte`, `contains`, `empty`, `notEmpty`), «Безусловный переход».
**Действия:** «Показать модуль», «Скрыть модуль», «Записать в узел
данных», «Перейти на адрес», «Показать сообщение», «Отправить
сигнал», «Отправить форму», «Отправить в CRM».

Действия «Отправить форму» и «Отправить в CRM» помечены как серверные:
их исполняет рантайм, и по манифесту видно, что такой сборке нужен
рантайм на сервере.

## Что проверяется до сборки

Пакет с логикой, которая падает на полпути, хуже отказа: сайт у
посетителя ломается в тот момент, когда он нажимает кнопку. Поэтому
проверка идёт до сборки и перечисляет все проблемы разом:

* неизвестный тип ноды, не заполненное обязательное поле, значение
  вне списка допустимых;
* связь в несуществующую ноду, нода соединена сама с собой;
* входящая связь у активатора, исходящая у действия, связь из условия
  без ветки, две связи из одной ветки;
* цикл — иначе цепочка исполнялась бы вечно.

Ндостижимость — предупреждение, а не ошибка: ноду могли оставить на
будущее. Но сказать об этом надо, иначе человек ищет, почему его
логика не сработала.

## Компиляция

Каждая нода становится функцией. Так сделано не из любви к функциям:
условие с ветками «да» и «нет» внутри выражения теряло бы одну из
них, а вложенное условие — обе.

Компиляция детерминированная: тот же граф даёт тот же файл, иначе две
сборки одной версии различались бы побайтно и сравнивать их было бы
нечем. Порядок обхода зафиксирован — по идентификатору ноды, а не по
порядку в документе: перестановка нод в редакторе не должна менять
сборку целиком.

Текст пользователя экранируется: `<`, `>`, `&` и разделители строк
заменяются на escape-последовательности, иначе значение с `</script>`
закрыло бы тег и сломало страницу.

В пакет кладутся:

* `assets/js/logic.js` — скомпилированная логика, подключается всегда,
  даже когда граф пуст (пустой граф даёт корректный файл, который
  ничего не делает);
* `logic.json` — декларация графа для рантайма, только если граф не
  пуст;
* в `build-manifest.json` — счётчики нод и признак того, что сборке
  нужен рантайм.

## API редактора

| Маршрут | Что делает |
|---|---|
| `GET /api/logic/types/` | библиотека нод для левой панели |
| `GET /api/projects/<id>/logic/` | граф проекта и результат проверки |
| `POST /api/projects/<id>/logic/check/` | проверка присланного графа и предпросмотр файла |

Ответ всегда содержит результат проверки: интерфейс показывает
проблемы прямо в редакторе, а не после неудачной сборки. Предпросмотр
собирает файл тем же кодом, что и сборка, — два пути разошлись бы
однажды.

## Редактор

`apps/web/src/ui/LogicScreen.tsx` — отдельный полноэкранный режим
(ТЗ п.4.2): библиотека нод слева, сетка со связями по центру,
свойства выбранной ноды справа.

Рисуем сами, без библиотеки для графов: правил соединения три, а
лишняя зависимость весила бы больше всей остальной логики экрана.

Как работает:

* нода добавляется нажатием на тип в библиотеке и раскладывается
  лесенкой по сетке;
* нода перетаскивается мышью за саму себя;
* связь проводится от кружка выхода: у активатора один выход, у
  условия два — «да» и «нет», у действия выхода нет вовсе;
* клик по линии убирает связь;
* «Сохранить логику» сначала спрашивает у сервера проверку графа и
  показывает скомпилированный файл, и только потом пишет его в
  документ проекта.

Дерево проекта запрашивается самим экраном, а не передаётся из
редактора: редактор держит своё состояние и сохраняет сам, и
переданный снимок к моменту открытия уже не соответствовал бы
серверу.

## Проверка ссылок на блоки

Ноды вида «Показать модуль» и «Отправить форму» ссылаются на блок
страницы. Такой ссылки на несуществующий блок сервер не пропускает:
внешне нода выглядит исправно и молча ничего не делает, а человек
ищет, почему. Проверка живёт в `validate_tree` и срабатывает при
сохранении документа, а не при публикации — иначе узнать об ошибке
пришлось бы через неделю после того, как логику собрали.

## Чего здесь нет

* **Выполнение логики на сервере.** Серверные ноды объявлены и
  попадают в декларацию для рантайма; их исполнение — часть
  рантайма (ADR-0005).
* **Отладка по шагам.** Проверка графа статическая: она ловит
  структурные ошибки, но не говорит, что произойдёт при конкретных
  данных посетителя.
* **Группировка нод и комментарии.** Граф читается цепочкой; для
  больших схем понадобится группировка веток.
