# Интеграция с 1С: что нужно для стенда

Документ отвечает на вопрос «что купить, настроить и прислать, чтобы
начать этап 7». Основной источник — ТЗ п.7.5 (версия 4.1). Здесь нет
ничего, чего нет в ТЗ: только то, что нужно физически, плюс два места,
где ТЗ требует решения заказчика.

Дата: 3 октября 2026. Статус: ожидает закупки.

---

## 1. Главное: этап 7 стоит на этом

Без работающего стенда 1С этап 7 (интеграция) не начинается. Срок
поставки лицензий — 2–6 недель, поэтому закупку нужно запускать до
того, как фронтенд закончит этап 3. Это единственный пункт, который
блокирует график, и он не про код.

## 2. Что купить

| Позиция | Зачем | Оценка |
|---------|------|--------|
| Лицензия 1С:Предприятие 8.3 для разработчика | Стенд разработки и приёмки | 25 000 – 40 000 ₽ разово |
| Эталонная база 1С:Управление Торговлей 11 | Проверка KPI «синхронизация 1000+ товаров ≤ 5 минут» | Входит в лицензию |

Закупка подтверждена заказчиком 30.09.2026 («1С учтена»), внесена в ТЗ
п.7.5.3. Нужно определить только конкретного поставщика и вариант
лицензии (одна рабочая лицензия или две: для разработки и для приёмки).

## 3. Какая конфигурация нужна

Минимально — **1С:Управление Торговлей 11**: именно она нужна для KPI
на 1000+ позиций. Остальные конфигурации из ТЗ п.7.5.1 (Бухгалтерия
3.0, Розница 2.3, ERP 2, УНФ) проверяются позже, на стенде заказчика;
для разработки хватит УТ.

## 4. Что должно быть включено в 1С (работы на стороне 1С)

Без этого синхронизация физически не заработает: платформа обращается
к HTTP-сервисам, а их нужно написать в конфигурации.

1. **HTTP-сервис** с базовым URL вида `https://<хост>/hs/aurabuilder/`
   и префиксом обмена для мультитенантности.
2. **HTTP Basic** на пользователя 1С с правами на чтение справочников
   «Номенклатура» и «Контрагенты», на запись документа
   «Заказ клиента». Для чувствительных контуров — клиентский
   сертификат (mTLS), это отдельное решение.
3. **Постраничность**: ответы обязаны поддерживать `page` и `size`
   (размер страницы — 500). Если конкретная конфигурация не умеет,
   пагинация делается на стороне платформы, и это надо знать заранее.
4. **Формат обмена**: JSON. Даты — ISO 8601 с часовым поясом
   `Europe/Moscow`, кодировка UTF-8. Для конфигураций без JSON —
   XML (клиент на zeep, MIT).
5. **Идемпотентность**: каждый объект передаётся с внешним ключом —
   GUID 1С. Повторная отправка того же GUID не создаёт дубль. Без
   этого повторная синхронизация задвоит товары и заказы.
6. **Ответ на запись заказа** должен возвращать `ref` (GUID созданного
   документа) — по нему платформа связывает заказ.

## 5. Что прислать для начала разработки

- Доступ к стенду: URL, логин, пароль (или сертификат).
- IP-адрес платформы, которому разрешён доступ (с нашей стороны нужен
  белый список IP, если доступ ограничивается firewall 1С).
- Согласованный период синхронизации: по умолчанию товары каждые
  15 минут, заказы — каждые 5 минут, полная выгрузка — раз в сутки.
  Если нужны другие интервалы, они меняются до начала этапа 7.
- Описание маппинга полей в терминах заказчика: соответствие
  «Номенклатура» → товары, «Контрагенты» → клиенты, «Заказ клиента» →
  заказы. ТЗ п.7.5.3 задаёт поля; уточнить нужно конкретные
  наименования реквизитов в их конфигурации.

## 6. Данные в эталонной базе

Минимум 1000 позиций номенклатуры с заполненными ценами и остатками —
иначе KPI «синхронизация ≤ 5 минут» нечем измерять. Реалистичные
данные, не «ТестоваяТовар1…ТестоваяТовар1000»: с ними сразу видны
проблемы с длиной наименований, переносами и выгрузкой контрагентов.

## 7. Приёмочные сценарии

ТЗ п.7.5.3 требует набор сценариев; каждый должен быть воспроизводим
на стенде заказчика:

1. Полная выгрузка каталога.
2. Инкрементальная выгрузка (только изменения после метки времени).
3. Обработка ошибок: недоступный 1С, таймаут, битый ответ, ошибка
   прав доступа.
4. Конфликт приоритетов: товар изменён и в 1С, и в платформе —
   побеждает 1С (ТЗ п.7.5.6).
5. Повторная отправка того же объекта — дубль не создаётся.
6. Передача заказа в 1С и обратная выгрузка его статуса.

## 8. Что НЕ нужно и что риск

- **Не нужен** 1С-сервер в нашем Docker Compose. Стенд живёт у
  заказчика или на отдельной машине: лицензия 1С не свободно
  распространяется, и в наш контур она попадать не должна.
- **Не нужен** боевой доступ к продакшен-базе заказчика. Только
  тестовый контур.
- **Риск сроков**: 2–6 недель на лицензию плюс время на настройку
  HTTP-сервисов на стороне 1С. Если сервисы ещё не написаны, этап 7
  начнётся позже на срок их разработки — это единственный пункт,
  который нельзя ускорить кодом.

## 9. Смежные решения (нужны заказчику, не блокируют)

- `data.related` и другие узлы для 1С-маппинга: состав узлов данных
  согласуется перед этапом 7.
- Хранение учётных данных 1С: шифрование AES-256 при сохранении,
  в памяти — plaintext (ТЗ п.7.5.2). Ключ хранения — на стороне
  платформы, он не в коде.
- Уведомления об ошибках синхронизации — письма через Яндекс 360
  (ТЗ п.7.6.1); адрес для оповещений нужно указать.
