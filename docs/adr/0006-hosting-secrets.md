# ADR-0006. Секреты профилей хостинга хранятся как есть, шифрование — на этапе 7

- **Статус:** исполнено, шифрование реализовано в ADR-0007
- **Дата:** 2026-10-13
- **Связано с:** ТЗ п.7.3, `apps/deploying/models.py`, `apps/deploying/views.py`

## Контекст

Деплой (ТЗ п.16.5) требует доступа к серверу заказчика: логина и
пароля или ключа. Значит, платформа впервые хранит чужой секрет, а не
свой собственный.

ТЗ п.7.3 требует AES-256 для чувствительных данных в базе. Пароль от
доступа к серверу заказчика — чувствительные данные, и требование
относится к нему напрямую.

Шифрование в покое требует ключа, а ключ где-то хранится. Ключ в
переменной окружения решает задачу ровно настолько, чтобы её не было:
при утечке базы без ключа данные защищены, при утечке окружения — нет.
Разница появляется только вместе с управлением ключами, которого в MVP
нет.

## Решение

*(принято на этапах 5–6; на этапе 7 реализовано шифрование — см. ADR-0007)*

На этапах 5–6 секрет хранится в базе без шифрования. Компенсирующие
меры, которые не требуют ключа:

* секрет не отдаётся в API никогда — ни при создании профиля, ни при
  чтении, ни в журнале действий; наружу уходит только признак «задан»;
* пустой секрет при правке означает «оставить прежний», иначе
  переименование профиля обнулило бы пароль и следующий деплой упал бы;
* доступ к профилю имеет только владелец проекта: участник видит
  список, но не может добавить или изменить доступ к серверу;
* деплой пишет в журнал действий идентификатор профиля, а не логин и
  не пароль.

Шифрование переносится на этап 7 вместе с управлением ключами: ключ в
HSM или в отдельном сервисе хранения секретов, ротация при смене
доступа. До этого момента риск ограничен копией базы платформы и
закрывается правами доступа к ней.

## Последствия

- Требование ТЗ п.7.3 про AES-256 выполняется не для этих данных и
  должно быть отражено как исключение в документах приёмки.
- Перед выпуском в бету нужен отдельный разбор: где живёт ключ и кто его
  ротирует. Это нельзя решить «быстро добавить шифрование» — ключ без
  управления им хуже, чем его отсутствие, потому что создаёт ложное
  ощущение защищённости.
- При переносе проекта на другой сервис секреты профилей переносятся
  отдельно и не должны попасть в архив проекта.

## Отвергнутые варианты

| Вариант | Почему не подходит |
|---------|--------------------|
| Шифровать ключом из переменной окружения | Ключ живёт рядом с базой; при утечке базы защищает, при утечке окружения нет, а обслуживания требует столько же |
| Не хранить секрет, просить при каждом деплое | Деплой нельзя запустить из cron и без браузера, доступ утекает в историю и журналы |
| Отдельное хранилище секретов с первого дня | Сервис без пользователя и без требований к доступности: инфраструктура, которая ничего не решает на этапе MVP |
