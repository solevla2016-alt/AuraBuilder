# Каталог модулей AuraBuilder

Предложение по перечню модулей (секций) редактора. Закрывает пробел ТЗ п.4.8
(п.3.3 вводит термин «Модули / Секции», но перечень отсутствовал).

## Принципы построения

1. **Модуль — атомарная единица контента.** Секция отвечает на вопрос «что это
   за блок», а не «как он выглядит». Внешний вид задаётся глобальными стилями
   (п.3.1, Смарт-Компоненты), а не отдельными модулями.
2. **Один модуль — много вариантов отображения.** Например, «Галерея» имеет
   сетку, карусель, слайдер. Варианты переключаются в настройках модуля, а не
   создаются как новые модули. Иначе библиотека разрастётся дубликатами.
3. **Разделение по назначению, а не по внешнему виду.** Пользователь выбирает
   «Блог», а не «Карточки со скруглёнными углами».
4. **Привязка к данным.** Каждый модуль, работающий с контентом, умеет
   привязываться к узлу данных (п.3.2, Data Node) — это основа совмещения с
   визуальной CMS.
5. **Термины ТЗ обязательны:** модуль, секция, узел данных, активатор, сигнальный
   мост. Названия конкурентов не используются (п.15.2).

## Категории и состав

### A. Структурные секции
Базовые контейнеры, определяющие композицию страницы.

| ID | Модуль | Назначение | Примечание |
|----|--------|-----------|------------|
| `section.header` | Шапка | Логотип, навигация, действия | Sticky-вариант, мобильное меню |
| `section.hero` | Первый экран | Заголовок, подзаголовок, CTA, фон | Fullscreen и компактный варианты |
| `section.feature` | Преимущества | Сетка 2/3/4 колонки с иконками | Иконки — только собственная библиотека (п.5.3) |
| `section.split` | Две колонки | Контент + медиа | Смена сторон, выравнивание по центру |
| `section.cards` | Карточки | Универсальная сетка карточек | Слот для изображения, текста, действия |
| `section.gallery` | Галерея | Сетка, карусель, мозаика | Lazy loading обязателен (п.8.2) |
| `section.steps` | Шаги | Нумерованный процесс | Горизонтальный и вертикальный вариант |
| `section.tabs` | Вкладки | Переключаемые панели | ARIA-разметка обязательна (п.5.1.1) |
| `section.accordion` | Аккордеон | Раскрывающиеся блоки | FAQ-вариант с микроразметкой Schema.org |
| `section.timeline` | Таймлайн | События по датам | Вертикальный и горизонтальный |
| `section.cta` | Призыв к действию | Контрастный блок с кнопкой | Фоновая подсветка, вариант «лента» |
| `section.footer` | Подвал | Навигация, контакты, реквизиты | Обязательные ссылки: политика, оферта |
| `section.spacer` | Отступ | Пустой раздел-разделитель | Адаптивная высота |

## Состав по этапам

| Этап | Категория | Модулей | Оценка |
|------|-----------|---------|--------|
| 3 | A (структурные) | 13 | 3 нед |
| 3 | B (контентные) | 19 | 3 нед |
| 5 | C (данные) | 12 | 4 нед |
| 6 | D (коммерческие) | 12 | 3 нед |
| 5–6 | E (доверие) | 9 | 1,5 нед |
| **Итого** | | **65** | **~15 нед** |

> Оценка — для одного фронтенд-разработчика при наличии готового каркаса
> редактора. Этап 3 в ТЗ = 3 месяца на весь редактор, включая холст Konva,
> контекстную панель и адаптивность. **65 модулей в этот срок не помещаются.**

## Что предлагаю изменить в плане

Три варианта:

**Вариант 1 — сократить MVP до 28 модулей.** Только то, без чего не собрать
лендинг и визитку: 8 структурных + 12 контентных + 8 данных. Категории D и E
переносятся в этапы 6–7. Оценка этапа 3: 4–5 недель вместо 8.

**Вариант 2 — расширить команду.** Добавить второго фронтенд-разработчика на
этапы 3–5. Стоимость: +3 месяца аренды в смете (п.14.1 не закладывает).

**Вариант 3 — разделить редактор на два режима выпуска.** «Блочный» с базовым
набором 28 модулей выпускается на этапе 3, остальные 37 модулей добавляются
инкрементально до этапа 6 без изменения архитектуры.

**Рекомендация:** вариант 3. Архитектура модулей не меняется, MVP появляется
рано, полнота достигается к этапу 6.

## Открытые вопросы по каталогу

1. **Аккордеон + FAQ** — один модуль с двумя режимами или два отдельных?
   Предлагаю один с переключателем и автогенерацией Schema.org в режиме FAQ.
2. **`data.form` в MVP?** Редактирование записей из публичного сайта — заметная
   доля безопасности и 152-ФЗ. Предлагаю: создание записи в MVP, редактирование
   и удаление — после бееты.
3. **Пользовательские модули.** Нужна ли возможность пользователю написать свой
   модуль? Если да — это отдельный проект (песочница, манифест, версионирование).
   Предлагаю отложить.
4. **Локализация.** Сколько языков на старте? Модули с подписями, alt-текстами и
   форматами дат требуют полноты переводов, иначе — «русский + английский».
