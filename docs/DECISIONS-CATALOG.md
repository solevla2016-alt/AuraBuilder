## 1. `data.form` — редактирование с публичного сайта

### Что зависит от ответа

| Затронутая область | Почему это не модуль, а архитектурное решение |
|---|---|
| **Модель прав** | Публичная запись = внешний пользователь пишет в БД проекта. Появляется третья роль поверх Owner/Admin/Editor/Dev/Viewer — «посетитель». Нужна отдельная модель прав на уровне записи, а не на уровне проекта |
| **Аудит (152-ФЗ)** | Каждая запись с ПДн требует журнала: кто, когда, что, IP (п.11.2). Пишет аноним — аудит усложняется кратно |
| **Транзакции и целостность** | Публичная запись конкурирует с редактором за данные. Нужны блокировки версий, которые в MVP не предусмотрены |
| **Экспорт (п.16.4)** | В статический архив форма отправки **не попадает**. Статический сайт не умеет принимать POST. Форма деградирует в заглушку или требует внешний обработчик. Это ломает заявленное «работает автономно» |
| **Стоимость MVP** | Реализация CRUD + аудит + защита от спама — минимум 2 недели работы сверх оценки этапа 3 |

### Что я предлагаю

**Разделить по режимам:**

| Часть | Когда | Что именно |
|-------|-------|-------------|
| Создание записи | **этап 5** (модули данных) | `data.form` в режиме create-only |
| Редактирование | **после закрытой беты** | `data.form` в режиме update |
| Удаление | **после закрытой беты** | `data.form` в режиме delete |

**Обоснование:** создание записи — это append-only операция без конфликтов и без риска потери чужого контента. Редактирование и удаление требуют модели прав на запись, журналирования и защиты от чужих правок. Разница в сложности — 1 операция против 3 операций с полным набором проверок.

**Дополнительно:** для статического экспорта (п.16.4) модуль `data.form` должен явно помечаться как «не поддерживается в статике» и не попадать в архив. Иначе пользователь обнаружит неработающую форму уже после экспорта.

### Альтернатива, которую я отклоняю

Полный CRUD в MVP. Даёт быстрее «веб-приложение», но добавляет 2 недели к этапу 3 и требует аудита по 152-ФЗ до того, как появится сама инфраструктура аудита (этап 2 ещё не закончен).

## 2. Аккордеон + FAQ — один модуль или два

### Что зависит от ответа

| Затронутая область | Почему это не модуль, а архитектурное решение |
|---|---|
| **Микроразметка (п.8.1)** | FAQ обязан выдавать `FAQPage` в Schema.org — это требование из ТЗ. Обычный аккордеон выдаёт `WebPage` или `SiteNavigationElement`. **Разные схемы на один компонент** — источник ошибок: движок не сможет выбрать схему по контексту |
| **Семантика и доступность** | FAQ — пары «вопрос-ответ» (`<dl>/<dt>/<dd>` или специальная разметка). Аккордеон — набор сворачиваемых панелей. Для скринридеров это разные структуры |
| **Логика по умолчанию** | FAQ обычно раскрыт по умолчанию, аккордеон — свёрнут. Разные состояния при загрузке |
| **Переиспользование** | FAQ строится из `data.list` (вопрос-ответ из узла данных). Аккордеон — из произвольных блоков. Разные источники данных |

### Что я предлагаю

**Два отдельных модуля с общим низкоуровневым компонентом:**

| Модуль | ID | Назначение | Схема микроразметки |
|--------|-----|-----------|---------------------|
| Аккордеон | `section.accordion` | Свёрнутые/раскрытые панели произвольного содержимого | нет (или `SiteNavigationElement`) |
| FAQ | `section.faq` | Пары вопрос-ответ, привязанные к узлу данных | `FAQPage` |

**Обоснование:** оба строятся на одном внутреннем компоненте `Disclosure` (поэтому код не дублируется), но **различаются контрактом** — разные схемы микроразметки, разная семантика, разная роль `isFAQ`. Смешивать их в один модуль значит зашивать в компонент условие «если это FAQ — делать то, иначе — это», что делает оба сценария хрупкими.

Это тот же принцип, что в п.4.5: «один модуль — много вариантов отображения», но вариант должен менять **смысл**, а не только вид. Разные схемы микроразметки — это разные модули.

### Альтернатива, которую я отклоняю

Один модуль с переключателем «режим FAQ». Экономит ~300 строк кода, но создаёт баг «настройка режима потерялась при импорте проекта» и усложняет валидацию микроразметки в Export Engine (п.16.2) — валидатор должен знать, какую схему ожидать.

## 3. Пользовательские модули — давать ли

### Что зависит от ответа

| Затронутая область | Почему это не модуль, а отдельный продукт |
|---|---|
| **Песочница** | Свой модуль = чужой JavaScript в рантайме. Нужна изоляция (iframe / Web Worker), лимиты CPU и памяти, запрет доступа к `window.parent`. Это инженерная задача на несколько недель |
| **Безопасность** | Свой модуль — вектор для XSS, кражи токенов, майнинга. Нужен аудит и модель ответственности |
| **Экспорт** | Код модуля должен корректно собираться во всех 5 сценариях (п.16.3–16.7). Для чужого кода это не гарантировано: он может использовать браузерные API, недоступные в SSR |
| **Версионирование** | У стороннего модуля есть своя версия и свои зависимости. Нужен менеджер версий, совместимость с ядром редактора, миграции при обновлении платформы |
| **Модерация** | Публикуемые модули проходят через проверку на вредоносность. Это постоянный процесс с человеком, а не разовая задача |
| **Поддержка** | Пользовательские модули ломаются. Кто чинит? За чей счёт? |

### Что я предлагаю

**Не включать в MVP и в тарифы.** Вместо этого:

1. **Разрешить произвольный код внутри секции** — модуль `code.custom` уже есть в MVP (13 из 19 контентных). Он исполняется в iframe-песочнице с ограничениями. Это закрывает потребность продвинутых пользователей (роль Dev по п.11.1) без инфраструктуры сторонних модулей.
2. **Спроектировать точку расширения** — описать контракт модуля как интерфейс (свойство, версия, зависимости, слоты, точки интеграции с логикой). Когда появится спрос и резерв времени — сторонние модули станут возможны без переделки ядра.
3. **Enterprise** — если клиент покупает коробку (п.17.4), можно разрешить установку подписанных модулей из реестра заказчика, без публичной маркетплейс-механики.

**Обоснование:** экономия ~4–6 недель на этапах 3–4. При этом `code.custom` в iframe закрывает ~80% реальных кейсов (вставка виджета, нестандартная вёрстка, embed). Платформа для маркетплейса модулей — это отдельный продукт с отдельной командой; смешивать его с редактором значит отвлекать 2 фронтенд-разработчиков от задач этапа.

### Риск, который это создаёт

Если пользователям **понадобится** кастомный модуль на этапе 5–6, разрыв будет болезненным: контракт модуля уже зафиксирован к тому моменту. Поэтому пункт 2 выше (спроектировать контракт заранее) обязателен — это ~2 дня работы на этапе 0.

## 4. Языки — сколько на старте

### Что зависит от ответа

| Затронутая область | Почему это не косметика |
|---|---|
| **Архитектура БД** | Поле `title` — это `title_ru` или `title` + таблица переводов? Решение принимается в модели данных (этап 2) и **не миграцией** |
| **Формы** | Подписи полей, тексты ошибок валидации, сообщения CAPTCHA (п.7.7 ур.7) — минимум 10 строк на модуль × 65 модулей |
| **Микроразметка** | `lang` и `hreflang` в SEO-разметке (п.8.1) |
| **Даты и числа** | Формат дат, разделители, валюты — различаются по локали. Ошибка здесь ломает SEO и доверие |
| **ИИ-генерация** | Промпты к YandexGPT (п.7.4) придётся локализовать тоже |
| **Цена ошибки** | Миграция схемы данных после выхода на рынок = простой всех проектов |

### Что я предлагаю

**Два языка контента: русский и английский. Один язык интерфейса: русский.**

| Слой | Языки | Когда |
|------|-------|-------|
| Интерфейс редактора и панели администратора | RU | MVP |
| Контент сайтов (страницы, подписи полей, тексты модулей) | RU + EN | MVP |
| Справочные тексты, системные уведомления | RU | MVP |
| Админка / биллинг | RU | MVP |

**Обоснование:** контент сайтов должен быть многоязычным с первого дня — это решение на уровне схемы БД (этап 2), и менять его после появления пользовательских проектов дорого. Интерфейс редактора оставляем русским: вся команда разработки русскоязычная, перевод интерфейса не входит в задачи ни одного этапа.

**Как реализовать без усложнения MVP:**

- Таблица переводов `i18n_string(key_ru, key_en)` вместо `i18n_string(key)`
- Модуль хранит только ключи переводов, не текст
- Локаль сайта — атрибут проекта, по умолчанию `ru`, выбор языка в URL (`/en/about`)
- `hreflang` генерируется автоматически Export Engine (п.16.2)

Затраты: ~1 неделя на этапе 2 сверх плана. Экономия: та же неделя, если переделывать на этапе 5–6, плюс миграция всех существующих проектов.

### Альтернатива, которую я отклоняю

**Только русский в MVP, остальные языки — потом.** Экономит 1 неделю сейчас, но требует миграции схемы БД и всех 65 модулей позже, когда появятся платящие клиенты с запросом на второй язык. Миграция данных — самая дорогая операция в проекте.
