# One-Click Deploy

Сценарий 3 ТЗ п.16.5: сайт работает на серверах заказчика, а
управляется через AuraBuilder. Здесь описано, что именно делает деплой и
что он принципиально не делает.

## Что происходит

1. Собирается статический пакет проекта — тот же, что отдаётся при
   выгрузке (ТЗ п.16.4), с проверенными HTML, SEO-файлами и без внешних
   ссылок.
2. Файлы кладутся на сервер, устаревшие удаляются: старый `index.html`
   после пересборки остался бы на месте, и сайт показывал бы его.
3. Рядом с сайтом появляется каталог `.aurabuilder/` — это рантайм:
   его файлы, `run.sh`, unit для systemd, правило для nginx и README
   для заказчика.
4. `runtime.json` в пакете получает адрес рантайма и ключ установки.
5. После загрузки выполняется проверка по HTTP: открывается ли главная
   и отвечает ли рантайм.

## Чего деплой не делает

**Он не запускает процессы на сервере.** По FTP команды выполнять нельзя,
а закрытые API хостингов у каждого свои, меняются и требуют выданных
ключей. Обходить это «как-нибудь» означало бы либо дыру в безопасности,
 либо зависимость от шести разных API.

Поэтому запуск рантайма — одна команда на сервере:

```
sh public_html/.aurabuilder/run.sh
```

Инструкция кладётся рядом с файлами, и деплой говорит об этом в
отчёте. Это осознанное ограничение, а не недоделанность: ТЗ п.16.5
требует «автоматическую загрузку», и именно загрузка выполняется
автоматически.

## Способы доступа

| Профиль | Когда подходит |
|---------|----------------|
| Папка на диске | Проверки, локальный стенд, сервер, где платформа развернута рядом с сайтом |
| FTP | Timeweb, Beget, Selectel, Reg.ru, SpaceWeb, FirstVDS — у всех есть FTP, и он не меняется вместе с панелью |

SFTP и API хостингов не реализованы. FTP закрывает все шесть хостингов
из ТЗ; SFTP потребовал бы внешней библиотеки, а API — знания закрытых
интерфейсов каждого провайдера. Когда появится требование к SFTP,
добавляется транспорт в `apps/deploying/transports.py`: интерфейс уже
описан двумя методами.

## Права и секреты

* Деплоить может тот, кто публикует (роль Admin и выше) — так же, как
  выгружать (ТЗ п.17.1).
* Профиль хостинга добавляет и меняет владелец проекта. Участник
  видит список, но не может добавить доступ: ушедший из проекта не
  должен унести с собой чужой сервер.
* Пароль или ключ не отдаются в API никогда — ни при создании, ни при
  чтении. Наружу уходит только признак «секрет задан».
* Ключ установки (`siteKey`) создаётся при первом деплое и дальше не
  меняется: новый ключ обнулял бы корзины всех покупателей. Смена —
  осознанное действие с флагом `--rotate-key`.

Шифрование секретов в покое — отдельная задача (ADR-0006).

## Проверка результата

Деплой проверяет две вещи и говорит о каждой отдельно:

* главная страница отвечает HTTP 200;
* рантайм отвечает на `/api/runtime/health` с `ready: true` и той же
  версией протокола, что собрана в пакете.

Несовпадение версий считается провалом: файлы загружены, а три модуля
работать не будут, и сообщить об этом должен деплой, а не покупатель.

## Проверка в разработке и CI

```
python tools/check_deploy.py
```

Скрипт разворачивает проект в папку, поднимает сайт из выложенных
файлов, запускает рантайм выложенным кодом и убеждается, что деплой
сам себя подтверждает: первый раз — честно не подтверждает, второй —
подтверждает. В CI идёт шагом `verify`.

Ручная выкладка:

```
python manage.py deploy_site <uuid-проекта> --profile <uuid-хостинга>
python manage.py deploy_site <uuid> --profile Timeweb --no-verify
python manage.py deploy_site <uuid> --profile Timeweb --rotate-key
```

## Что осталось за кадром

* SFTP и API хостингов — см. «Способы доступа».
* Автоматический запуск службы: возможен только через API хостинга или
  SSH-команду, которых в платформе нет.
* SSL-сертификат: выпуск и обновление сертификата решает хостинг,
  платформа лишь проверяет, что сайт отвечает по HTTPS, если адрес
  указан с этой схемой.
