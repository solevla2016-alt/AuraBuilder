# Секреты и управление ключами (ТЗ п.7.3, ADR-0007)

Платформа хранит чужие секреты: пароль от сервера заказчика, а позже —
учётные данные 1С и токен бота. Все они шифруются AES-256-GCM и не
возвращаются через API никогда.

## Как это устроено

| Что | Где |
|---|---|
| Шифрование, кольцо ключей | `apps/secretstore/crypto.py` |
| Работа с секретом в модели | `apps/secretstore/services.py` (`SecretMixin`) |
| Пароль профиля хостинга | `apps/deploying/models.py`, поле `secret_encrypted` |
| Основание | ADR-0007 |

Значение в базе выглядит так: `a1.2026-10.<nonce>.<шифротекст>`. Первое
поле — версия формата, второе — идентификатор ключа, которым зашифровано
значение.

Шифротекст привязан к записи: скопировать его из одного профиля в
другой нельзя, чтение вернёт ошибку.

## Задание ключа

Ключ — 32 байта в base64url и идентификатор. Сгенерировать:

```bash
python manage.py secret_key --generate 2026-10
```

Результат (одна строка) положить в менеджер секретов платформы и
задать в окружении:

```
DJANGO_SECRET_ENCRYPTION_KEYS=2026-10:<ключ>,2026-04:<старый ключ>
```

Первый ключ в списке используется для шифрования, все — для
расшифровки.

**Ключа нет — платформа не хранит чужие пароли вовсе** и отвечает 503 с
объяснением. Это осознанный отказ: сохранить их открытыми значило бы
вернуть то, что шифрование убирает.

Проверить состояние кольца:

```bash
python manage.py secret_key
```

## Ротация

Порядок обязателен, нарушение ломает секреты:

```bash
# 1. Новый ключ добавлен первым в DJANGO_SECRET_ENCRYPTION_KEYS.

# 2. Значения перешифрованы новым ключом (старый ещё в кольце):
python manage.py rotate_secrets --dry-run   # посмотреть
python manage.py rotate_secrets             # выполнить

# 3. Старый ключ удалён из кольца.
```

Команда падает с ошибкой, если хоть одно значение не прочиталось: это
означает, что удалять старый ключ рано.

## Перенос существующих паролей

Миграция `deploying.0002_encrypt_hosting_secrets` переносит открытые
пароли в зашифрованное поле и удаляет открытое. Если ключ в момент
миграции не задан, значения переносятся как есть и остаются читаемыми:
терять доступ к серверам заказчиков из-за несвоевременно заданного ключа
хуже, чем временно оставить их открытыми.

Такие значения видно в интерфейсе: `secretEncrypted: false`. После
задания ключа их следует перешифровать:

```bash
python manage.py rotate_secrets
```

## Проверки

Тесты живут в `apps/secretstore/tests_secrets.py` и проверяют не
«зашифровалось ли», а свойства, на которых держится защита:

* значение в базе не содержит пароля;
* без ключа чтение невозможно, с чужим ключом — ошибка;
* подмена шифротекста и подстановка в другую запись обнаруживаются;
* старый ключ читает после ротации, повторный запуск безопасен;
* миграция переносит данные и удаляет открытое поле;
* без ключа миграция не теряет доступ и не падает.

## Чего здесь нет

* **Интеграция с 1С и токен бота.** Механизм общий, сами интеграции
  отложены (п.7.5.3 и сценарий 4).
* **Смена ключа по расписанию.** Ротация ручная: автоматическая ротация
  без планировщика просто добавит способ забыть про неё.
* **Интеграция с HSM/Vault.** Ключ хранится в окружении развёртывания;
  перенос в менеджер секретов зафиксирован в ADR-0007 как условие беты.
