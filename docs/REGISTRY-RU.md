# Реестр российского ПО: что нужно для закупок (этап 3)

Документ — рабочий чек-лист, а не юридическое заключение. Он собирает
факты о продукте, которые уже есть в репозитории, отделяет их от того,
что может дать только правообладатель, и показывает инженерные пробелы,
которые закрываются кодом. Точные формулировки требований и перечень
документов проверяются по актуальной редакции постановления и регламенту
Минцифры на дату подачи: правила меняются чаще, чем продукт.

Зачем это нужно: включение в реестр — условие закупок по 44-ФЗ и 223-ФЗ
для многих заказчиков. Это не сертификация безопасности и не заменяет
испытания; реестр подтверждает происхождение и российские права на ПО.

## Что заявляем

| Параметр | Значение |
|---|---|
| Продукт | AuraBuilder — конструктор сайтов и веб-приложений |
| Версия | `0.1.0` (`package.json`, `docs/sbom.json`) |
| Редакции | облако и self-hosted; один код, режим задаётся `DEPLOYMENT_MODE` |
| Назначение | сборка страниц из модулей, публикация, аналитика, заявки, интеграции |
| Правообладатель | **не указан: требуется от заказчика** |

Класс ПО по классификатору Минцифры нужно выбрать перед подачей. Продукт
попадает сразу в несколько соседних классов (средства разработки,
управление контентом, хостинг сайтов), и выбранный класс определяет
формулировки описания. Это решение правообладателя, а не разработки.

## Правообладатель

Исключительное право должно принадлежать российскому лицу, а структура
владения — исключать иностранный контроль в установленных пределах.
Проверять нужно не «российскую регистрацию» вообще, а конкретные доли и
цепочку владения на дату подачи.

Что понадобится:

- реквизиты: наименование, ИНН, ОГРН, адрес, ОКВЭД;
- документы на исключительное право: договоры об отчуждении, акты,
  служебные произведения с авторами, трудовые договоры;
- сведения о долях и конечных владельцах;
- подтверждение, что ПО правомерно введено в гражданский оборот;
- лицензионное соглашение или пользовательское соглашение для поставки.

В репозитории этого нет и быть не может. Пункты ниже, помеченные
«данные правообладателя», — единственный блок, который блокирует подачу.

## Что уже соответствует технически

Эти факты подтверждаются кодом и тестами, а не декларацией:

| Свойство | Где подтверждается |
|---|---|
| Работа без обязательных иностранных облаков | `DEPLOYMENT_MODE=self-hosted`, `docs/SELF-HOSTED.md` |
| Полностью офлайн-режим | локальный ИИ-провайдер, `docs/AI.md`; публикация и сборка без внешних сервисов |
| PostgreSQL допустим, есть путь к Postgres Pro | `psycopg`; матрица совместимости — в пробелах ниже |
| Резервное копирование и восстановление | `backup_platform` / `restore_platform`, `docs/SELF-HOSTED.md` |
| Состав зависимостей | `docs/sbom.json`, `npm run sbom` |
| Контроль лицензий | `tools/license-gate.mjs`, `tools/license_gate_py.py` |
| Отсутствие обязательной оплаты в поставке | `BILLING_ENABLED=False` снимает тарифные проверки |
| Воспроизводимая установка | `docker/`, `docker-compose.yml`, `docs/DEPLOY.md` |

Ключевое для закупок: продукт не перестаёт работать, если у заказчика нет
доступа к GitHub, Docker Hub, Telegram или YandexGPT. Внешние сервисы —
дополнения, а не ядро.

## Внешние компоненты и их роль

Реестр не запрещает открытые библиотеки, но требует раскрыть состав и
показать, что среди обязательных частей нет того, что противоречит
требованиям. Ниже — честная картина.

| Компонент | Происхождение | Роль | Обязателен в поставке |
|---|---|---|---|
| Python 3.13, Django 6.1 | открытый код, зарубежный проект | серверная платформа | да, как библиотека |
| React 19, Vite, Konva | открытый код, зарубежный проект | интерфейс редактора | да, как библиотека |
| PostgreSQL | открытый код | база данных | да (можно Postgres Pro) |
| Docker | открытый код | упаковка поставки | для контейнерной редакции |
| YandexGPT | российский сервис | ИИ-помощник | нет: локальные правила по умолчанию |
| Telegram Bot API | зарубежный сервис | Mini App и бот | нет: интеграция по желанию |
| Yandex 360 SMTP | российский сервис | письма | нет: без ключей письма идут в консоль |
| GitHub | зарубежный хостинг кода | разработка | нет: в поставку не входит |

Отдельно: хранение исходников на GitHub — отступление от ТЗ п.15.3 п.6,
уже зафиксированное в README. Для реестра важен состав поставки, а не
место разработки, но при закупке заказчик может спросить об этом. Ответ:
исходники и обновления передаются ему по договору, а self-hosted Forgejo
остаётся вариантом для Enterprise.

## Комплект документов

Порядок и формы подаются через портал Минцифры (Госуслуги). Ниже —
типовой состав; перед подачей сверять с действующим регламентом.

1. **Заявление** о включении в реестр — данные правообладателя.
2. **Сведения о правообладателе** — реквизиты, структура владения.
3. **Документы на исключительное право** — договоры, акты, служебные
   произведения.
4. **Функциональное описание** — что делает продукт, какие задачи решает,
   чем отличается; основа — README и `docs/MODULE-CATALOG.md`.
5. **Сведения о компонентах и лицензиях** — `docs/sbom.json` плюс короткая
   пояснительная записка о роли внешних сервисов (таблица выше).
6. **Лицензионное соглашение** — сейчас в репозитории `UNLICENSED`, его
   нужно подготовить (см. пробелы).
7. **Подтверждение работоспособности** — инструкция установки
   (`docs/SELF-HOSTED.md`), акт проверки, скриншоты.
8. **Сведения о соответствии классу** — выбранный класс и обоснование.

## Порядок и сроки

1. Правообладатель собирает комплект и подаёт заявление.
2. Минцифры проводит экспертизу; по общему правилу она занимает до
   30 рабочих дней, но срок зависит от редакции регламента и полноты
   документов.
3. По результатам — включение в реестр либо мотивированный отказ.
4. После включения сведения нужно поддерживать актуальными: сообщать об
   изменениях продукта и правообладателя в установленные сроки.

Практический вывод: подача — проект правообладателя на месяцы, а не
задача разработки на день. Инженерная часть должна быть готова заранее,
иначе экспертиза упрётся в отсутствие лицензионного соглашения или
описания компонентов.

## Инженерные пробелы до подачи

| Пробел | Почему мешает | Что сделать |
|---|---|---|
| Лицензионное соглашение отсутствует (`UNLICENSED`) | без него непонятны условия поставки и использования | подготовить EULA/пользовательское соглашение, проверить юристом |
| Нет подтверждённой матрицы совместимости с российскими ОС | закупки часто требуют Astra Linux / Red OS | прогнать контейнеры и тесты на Astra Linux SE, зафиксировать результат |
| Postgres Pro не проверен отдельно | заказчик может требовать российскую СУБД | прогнать тесты на Postgres Pro, добавить в матрицу |
| Артефакты релиза не версионируются как поставка | экспертизе нужен конкретный дистрибутив | собирать релизный архив с контрольными суммами и манифестом |
| SBOM не обновляется в CI | состав зависимостей разъедется с поставкой | добавить `npm run sbom` в проверку релиза |
| Нет публичной страницы продукта с описанием | нужна для заявки и закупок | подготовить текст на основе README, без обещаний вне продукта |

Эти пункты не блокируют работу платформы, но блокируют заявку. Их можно
закрывать по одному, не дожидаясь юридической части.
