# Self-hosted: установка на сервере заказчика

Self-hosted — это не отдельная сборка, а режим того же пакета. Один
образ, один код, один API: в облаке открыта регистрация и работают
тарифы, на сервере заказчика регистрация закрыта, а тарифных проверок
нет. Поэтому обновления, исправления безопасности и интеграции (1С,
Telegram, вебхуки) приезжают сюда так же, как в облако.

Режим задаётся переменной `DEPLOYMENT_MODE`:

| Значение | Регистрация | Тарифы |
|----------|-------------|--------|
| `cloud` (по умолчанию) | открыта | включены |
| `self-hosted` | закрыта | отключены |

Оба флага можно переопределить явно: `ALLOW_REGISTRATION=1` откроет
регистрацию, `BILLING_ENABLED=1` вернёт тарифные проверки. Пустое
значение означает «как в режиме».

Технические лимиты (`LIMIT_*` в `apps/controlplane/settings.py`) в
self-hosted остаются: они защищают сервер от одного проекта на десять
тысяч блоков, а не продают место.

## Что нужно

* Docker Engine и Docker Compose v2;
* домен, направленный на сервер, и TLS-сертификат (обычно на прокси
  перед контейнерами);
* PostgreSQL 15+ — в compose уже входит PostgreSQL 18;
* минимум 2 ГБ RAM и место под тома: база, `publish-data`,
  `asset-data`, `backup-data`. Размер копии примерно равен сумме базы
  и обоих каталогов.

Внешняя сеть нужна только при сборке образа (pip и npm) и для
интеграций, которые заказчик включает сам. Публикация и выгрузка
статики работают офлайн: собранный сайт не обращается к платформе.

## Установка с нуля

```bash
git clone <репозиторий> aurabuilder
cd aurabuilder
cp .env.example .env
```

В `.env` обязательно:

```ini
DEPLOYMENT_MODE=self-hosted
DJANGO_SECRET_KEY=<длинный случайный ключ>
POSTGRES_PASSWORD=<пароль базы>
DJANGO_ALLOWED_HOSTS=cms.example.ru
DJANGO_DEBUG=0
```

Ключ Django генерируется так:

```bash
python -c "import secrets; print(secrets.token_urlsafe(64))"
```

Если нужны Telegram, 1С или деплой на чужой хостинг, добавьте кольцо
ключей шифрования секретов. Без него платформа честно ответит 503 на
попытку сохранить чужой пароль, а не сохранит его открытым:

```bash
docker compose build api
docker compose run --rm --no-deps api python manage.py secret_key --generate 2026-01
# полученное значение — в DJANGO_SECRET_ENCRYPTION_KEYS
```

Затем:

```bash
docker compose up --build --wait
```

Первый владелец создаётся командой, а не через регистрацию:

```bash
docker compose exec -e STEND_OWNER_PASSWORD='<пароль>' api \
  python manage.py create_owner --username owner
```

Пароль через переменную, а не `--password`: аргумент остался бы в
истории командной строки. Команда идемпотентна; повторный запуск с
`--reset-password` меняет пароль существующего владельца.

Дальше: <http://localhost:8080> (или ваш домен через прокси), вход под
`owner`, создание проекта и публикация. Адрес опубликованного сайта
задаётся `PUBLICATION_BASE_URL`, адрес платформы для Mini App и кнопок
бота — `PLATFORM_BASE_URL`. Оба должны быть внешними: `127.0.0.1` в
ссылке бота выглядит рабочим только на сервере.

### TLS и прокси

TLS терминируется на прокси, а не в gunicorn. Прокси обязан передавать
`X-Forwarded-Proto`, а в `.env` должно быть:

```ini
DJANGO_TRUST_FORWARDED_PROTO=1
DJANGO_CSRF_TRUSTED_ORIGINS=https://cms.example.ru
```

`DJANGO_SECURE_SSL_REDIRECT=1` (значение по умолчанию при `DEBUG=0`)
перенаправляет http на https. Если прокси не передаёт заголовок,
получится цикл редиректов — это самая частая ошибка установки.

## Обновление

```bash
git pull
docker compose up --build --wait
```

Сервис `migrate` накатывает миграции до старта `api`. Откат образа без
отката схемы не поддерживается: сначала восстановите копию, снятую до
обновления.

## Резервное копирование

Копия включает:

* базу (SQLite — согласованный снимок через backup API, PostgreSQL —
  `pg_dump` в custom-формате);
* `PUBLISH_ROOT` — опубликованные сайты;
* `ASSET_ROOT` — картинки медиатеки;
* `MEDIA_ROOT`, если он задан;
* `manifest.json` с временем, режимом, СУБД и контрольными суммами.

Не включает: `.env`, `DJANGO_SECRET_KEY`, пароль PostgreSQL, TLS-сертификаты.
Их храните отдельно. Ключи шифрования секретов можно добавить только
явным флагом — см. ниже.

```bash
docker compose exec api python manage.py backup_platform \
  --output /backup/aurabuilder-$(date +%Y%m%d-%H%M%S).tar.gz
```

Каталог `/backup` — том `backup-data`. Забирать архивы с сервера нужно
регулярно: том защищает от пересборки контейнера, но не от потери
диска.

Ежедневный запуск на хосте:

```cron
15 3 * * * cd /opt/aurabuilder && docker compose exec -T api \
  python manage.py backup_platform \
  --output /backup/aurabuilder-$(date +\%Y\%m\%d).tar.gz
```

`-T` обязателен в cron: без терминала `docker compose exec` пытается
выделить TTY и падает.

### Ключи шифрования в копии

```bash
docker compose exec api python manage.py backup_platform \
  --output /backup/with-keys.tar.gz --include-secret-keys
```

Флаг кладёт `DJANGO_SECRET_ENCRYPTION_KEYS` отдельным файлом `keys.env`.
Без этих ключей восстановленные секреты (пароли 1С, токены ботов,
доступы к хостингу) останутся зашифрованным мусором. С ними архив
становится таким же секретом, как пароль: храните его в защищённом
месте и не отправляйте по открытым каналам.

## Восстановление

Восстановление заменяет базу и каталоги. Остановите всё, что пишет и
раздаёт файлы:

```bash
docker compose stop api scheduler web
docker compose run --rm --no-deps api \
  python manage.py restore_platform /backup/aurabuilder-20260101.tar.gz
```

Без `--yes` команда просит ввести слово `restore` — защита от запуска
не на той машине. `--yes` нужен только для автоматизации.

Порядок внутри команды:

1. архив распаковывается во временный каталог;
2. проверяются формат, версия и контрольные суммы — при расхождении
   ничего не меняется;
3. СУБД архива сверяется с текущей (дамп PostgreSQL нельзя загрузить в
   SQLite);
4. старое содержимое каталогов переезжает в
   `<каталог>.before-restore-<время>` рядом с рабочим;
5. каталоги и база заменяются;
6. накатываются миграции — копия могла быть снята более ранней версией.

После этого:

```bash
docker compose up -d
```

Старые каталоги лежат рядом с томами (`/srv/published.before-restore-…`,
`/srv/assets.before-restore-…`). В контейнере они относятся к слою
образа, поэтому до пересоздания контейнера скопируйте нужное наружу:

```bash
docker compose cp api:/srv/published.before-restore-20260101-030000 ./old-published
```

Если архив содержит ключи, команда положит их в `restore-keys.env` в
текущем каталоге. Сами по себе они не применяются: перенесите значение
в `DJANGO_SECRET_ENCRYPTION_KEYS` и перезапустите сервисы, иначе
восстановленные секреты останутся нечитаемыми.

Ограничения:

* восстановление возможно только в ту же СУБД;
* в образе `postgresql-client` версии 18. Клиент обязан быть не старше
  сервера, иначе `pg_dump` откажется снимать копию. Если сервер новее
  18, обновите образ;
* команда не заменяет `.env` и не восстанавливает TLS. Это
  конфигурация хоста, а не данные платформы.

## Приёмка установки

1. Чистый хост, `docker compose up --build --wait`.
2. `create_owner`, вход.
3. Создать проект, добавить картинку, опубликовать сайт.
4. `backup_platform`.
5. `docker compose down -v` — база и тома удалены.
6. `docker compose up -d db`, `restore_platform`, `docker compose up -d`.
7. Вход, проект на месте, картинка открывается, сайт по адресу
   публикации работает.

Пункт 5 уничтожает данные. На стенде это допустимо, на рабочем
сервере — только если копия уже снята и проверена.
