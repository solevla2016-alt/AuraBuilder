# Как вносить изменения

Документ о том, как проверять правку и что считается готовой. ТЗ
описывает, что строить; этот файл — как это доводить до зелёного
состояния.

## Что должно пройти перед отправкой

Полный набор — `npm run verify` в корне. Он же запускается в CI, и
проверять руками то, что делает пайплайн, не нужно.

```bash
npm run verify
```

По частям:

| Проверка | Что ломает |
|----------|-----------|
| `npm run registry:check` | Сгенерированные файлы разошлись с источником: токены, реестр модулей, схемы свойств |
| `npm run tokens:contrast` | Контраст палитры ниже порога WCAG |
| `npm run licenses` | Появилась зависимость с запрещённой лицензией |
| `npm run sbom -- --check` | Изменился состав зависимостей, а реестр не обновлён |
| `npm run typecheck` | Ошибки типов во фронтенде |
| `npm run build` | Фронтенд не собирается |
| `python tools/license_gate_py.py` | Python-зависимость с запрещённой лицензией |
| `manage.py test` | Тесты Django |
| `node tools/screenshot-editor.mjs http://127.0.0.1:8080/` | Браузерные сценарии |

## Правила, которые проверяются автоматически

Их нарушение нельзя пропустить, но легко допустить по незнанию.

**Лицензия зависимости.** ТЗ п.7.1.6 запрещает copyleft и
source-available: GPL, AGPL, SSPL, RSAL, BUSL, Elastic, CC-BY-NC.
Gate падает на такой пакет с указанием, что именно его принесло.
Исключения есть, и они описаны в `docs/TZ-GAPS.md` п.1.2.

**Состав SBOM.** После добавления зависимости обновите реестр:

```bash
npm run sbom
```

И закоммитьте `docs/sbom.json`. Без этого падает CI.

**Версии Python закреплены точно.** В `apps/requirements.txt` —
только `==`, без диапазонов: состав поставки должен быть известен,
а не воспроизводим приблизительно.

**Токены и реестр — генерируемые.** Править руками нельзя. Меняется
источник, затем выполняется генератор:

```bash
npm run tokens:build
npm run registry:build
```

CI проверяет, что результат совпадает с тем, что лежит в репозитории.

**Цвета берутся из `docs/palette.json`.** Дубликаты цветов в коде
ломают смену темы. То же касается отступов и радиусов: они описаны
в `docs/design-tokens.ts`.

## Когда заводить ADR

На каждое решение, которое нельзя вывести из кода: выбор технологии,
отказ от очевидного варианта, изменение правила проекта. Шаблон и
список — в `docs/ADR.md`.

Не заводится на структуру папок и имена классов: это видно в коде.

## Браузерные сценарии

Правка интерфейса без новой проверки в `tools/screenshot-editor.mjs`
считается незавершённой: сценарий — это и есть проверка интерфейса.
Правило простое — если правку можно сломать, у неё есть сценарий.

```bash
node tools/probe.mjs http://localhost:5173/ --eval "document.querySelector('main').className"
node tools/probe.mjs --login owner --password '...' --open-project --click 'селектор' --text '.селектор'
```

`probe.mjs` — для разбора неожиданного экрана, `screenshot-editor.mjs`
— для проверки. Первое открывает Chrome и оставляет его открытым с
`--keep`, второе прогоняет сценарии и падает на первом провале.

Сценарий падает, если собранный стенд старше последней правки в
`apps/web/src`. Это защищает от «забыл пересобрать»: сценарии идут
против старого бандла и проходят, ничего не проверяя.

## Работа с ТЗ

ТЗ лежит в `.docx` и редактируется скриптами, чтобы не потерять
форматирование:

```bash
python tools/tzedit.py map "AUIRA ТЗ.docx"
python tools/tzedit.py find "AUIRA ТЗ.docx" "7.5"
python tools/tzedit.py replace "AUIRA ТЗ.docx" "старое" "новое"
```

Правки к ТЗ и к коду — в одном коммите. Расхождение между ними
заметно только при сверке, а сверка происходит на приёмке.

## Стиль

- Комментарий объясняет **почему**, а не что делает код. «Что» видно
  из кода; «почему» исчезает вместе с ним.
- Идентификаторы, комментарии и пользовательский текст — по-русски.
- Никаких новых зависимостей без обновления `docs/sbom.json` и
  проверки лицензии.
- Сообщение об ошибке должно называть причину и, где возможно,
  показывать проверенные пути или значения. «Проверьте настройки»
  без подробностей не считается сообщением.
